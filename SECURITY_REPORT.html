2. Encryption & Data Protection

Encryption at Rest

  • Algorithm: AES-256-GCM (authenticated encryption — ciphertext integrity is cryptographically verified on every read, tampered data is rejected rather than silently decrypted)
  • Key derivation: scrypt, combined with a dedicated server-side encryption secret plus a unique random salt per record
  • IV: Fresh random Initialisation Vector for every encryption operation
  • Storage: Encrypted ciphertext, salt, IV and authentication tag stored in Firestore; the encryption secret is never stored alongside the data it protects
  • Key management: Encryption key stored as environment variable, never hardcoded

Encryption in Transit

  • Protocol: TLS 1.2 / 1.3 (HTTPS only in production)
  • HSTS: Strict-Transport-Security max-age=31,536,000; includeSubDomains; preload
  • Upgrade policy: CSP upgrade-insecure-requests directive enforces HTTPS
  • API traffic: All calls to Autodesk ACC API over HTTPS
  • Firebase: WebSocket over WSS (encrypted WebSocket)
Firestore (Google Cloud) Encryption
Google Cloud Firestore automatically encrypts all data at rest using AES-256 and all data in transit using TLS. This is in addition to the application-level AES-256-GCM authenticated encryption applied before data reaches Firestore — providing double-layer encryption, with integrity verification, for sensitive fields.
Secret / Key Storage
No credentials, API keys, or encryption keys are hardcoded in source code. All secrets are injected at runtime via OS environment variables and excluded from version control via .gitignore. The application fails with a fatal error on startup if any required secret is missing.
3. Authentication & Access Control
ControlImplementation
✔ Firebase Authentication Industry-standard identity platform (Google) with email / password authentication
✔ Email Verification Enforced server-side — non-admin accounts cannot log in until their email address is verified
✔ JWT Token Authentication All API requests authenticated using short-lived JSON Web Tokens issued by Firebase
✔ Firebase App Check (reCAPTCHA v3) Prevents automated / bot access to Firebase backend resources
✔ Role-Based Access Control (RBAC) Admin and standard user roles enforced server-side; admin checks performed in Firestore Security Rules
✔ Firestore Security Rules Server-side rules prevent any authenticated user from accessing another user's data
✔ Per-User Data Isolation Multi-tenant architecture — each user can only read/write their own data partition
✔ No Client-Side Credential Storage Session tokens are never written to localStorage or sessionStorage. The Autodesk API client secret is never sent to or held in the browser at all — the OAuth token exchange is performed entirely server-side
✔ OAuth State Parameter Validation A cryptographically random state value is generated and verified before any authorization code is exchanged, protecting the Autodesk login flow against cross-site request forgery
4. Application Security — OWASP Top 10 Compliance

The following table maps the OWASP Top 10 (2021) vulnerability categories to the controls implemented in the application.

OWASP CategoryStatusControls in Place
✔ A01 — Broken Access Control Mitigated Firebase Security Rules + server-side admin middleware; per-user data isolation
✔ A02 — Cryptographic Failures Mitigated AES-256-GCM authenticated encryption with scrypt key derivation from a dedicated server-side secret; TLS 1.2/1.3; HSTS enforced; the Autodesk API client secret is never transmitted to or held in the browser
✔ A03 — Injection / XSS Mitigated escapeHtml() function applied throughout; data originating outside the application (Autodesk project, hub, folder, company and role names; user-submitted emails shown in the admin panel) is rendered via safe DOM APIs (textContent / element properties) rather than HTML string concatenation; strict CSP blocks unauthorized script execution. A full audit of every dynamic HTML insertion point in the codebase (~100 locations) confirmed each is either non-dynamic (fixed markup with no interpolated content), interpolates only trusted internal values (counts, timestamps, fixed labels), or is explicitly escaped.
✔ A04 — Insecure Design Mitigated Threat-modelled architecture; secrets management via environment variables; no debug endpoints in production
✔ A05 — Security Misconfiguration Mitigated Comprehensive security headers (7 headers active); CORS restricted to allowed origins; no default credentials; static file serving is scoped exclusively to a dedicated public assets directory — server-side configuration and credential files are never web-accessible
✔ A06 — Vulnerable Components Mitigated Dependencies tracked in package.json; regular audit cycle
✔ A07 — Auth & Session Failures Mitigated Firebase-managed auth; short-lived JWTs; enforced email verification before login; rate limiting (5 login attempts / 15 min); CSRF-protected OAuth flow via validated state parameter
✔ A08 — Software Integrity Failures Mitigated CSP restricts script sources to explicit whitelist; external resources loaded from HTTPS CDNs only; Subresource Integrity (SRI) hashes verify every externally-loaded script matches its expected content before execution
✔ A09 — Logging & Monitoring Failures Mitigated Request logging with IP tracking; authentication event logging; error logging (non-verbose to users)
✔ A10 — Server-Side Request Forgery Mitigated Server only makes outbound requests to whitelisted Autodesk and Google endpoints; no user-controlled URL parameters passed to backend fetch calls
5. HTTP Security Headers

All production responses include the following security headers, providing defence-in-depth against common browser-based attacks:

HeaderValue / Description
✔ Strict-Transport-Security max-age=31536000; includeSubDomains; preload — Forces HTTPS for 1 year across all subdomains
✔ Content-Security-Policy Strict policy with default-src 'self'; frame-ancestors 'none'; form-action 'self'; object-src 'none'; upgrade-insecure-requests
✔ X-Frame-Options DENY — Prevents clickjacking by disallowing the application from being embedded in any iframe
✔ X-Content-Type-Options nosniff — Prevents MIME-type sniffing attacks
✔ X-XSS-Protection 1; mode=block — Activates browser's built-in XSS filter
✔ Referrer-Policy strict-origin-when-cross-origin — Limits referrer information sent to third parties
✔ Permissions-Policy geolocation=(), microphone=(), camera=() — Disables access to sensitive browser APIs not required by the application
6. Infrastructure & Hosting Security

Hosting Environment

  • Provider: Google Cloud Platform (VM)
  • Region: European data centre
  • Domain: usermgt.digibuild.ch (HTTPS)
  • Process manager: PM2 (auto-restart, single instance)
  • OS firewall: Only ports 80, 443, 3000 open

Database — Google Firestore

  • Provider: Google Firebase / Firestore
  • Managed, serverless NoSQL database
  • Automatic replication & backups
  • AES-256 encryption at rest (Google-managed)
  • TLS 1.3 encryption in transit
  • SOC 1, SOC 2, ISO 27001 certified

Rate Limiting & DoS Protection

  • Global API: 100 requests / 15 minutes per IP
  • Login endpoint: 5 attempts / 15 minutes per IP
  • Register endpoint: 5 attempts / 15 minutes per IP
  • Algorithm: Sliding window with Redis backend
  • Behaviour: Returns HTTP 429 on breach

Network & CORS Controls

  • CORS restricted to explicitly whitelisted origins only
  • No wildcard (*) origins in production
  • Credentials flag enabled only for allowed origins
  • Preflight requests validated server-side
  • HTTP→HTTPS redirect active in production
Google Cloud & Firebase Security Certifications: The underlying infrastructure (Google Cloud Platform and Firebase) holds the following certifications: ISO/IEC 27001, SOC 1 Type II, SOC 2 Type II, SOC 3, PCI DSS, FedRAMP and more. Full details: cloud.google.com/security/compliance and firebase.google.com/support/privacy.
